Vad bad vi AI:n att göra — och inte göra?

Projektets ramar

  • Kör lokalt; använd bara påhittade kunduppgifter.
  • TypeScript, React/Vite, Express och SQLite.
  • Små, vertikala features med egna krav och tester.

AI:n som assistent

  • Be om förslag när något är oklart — inte tysta antaganden.

03 · Vertikala features

Bygg en användbar bit i taget

I stället för en stor kravlista delade vi MVP:t i flöden som går genom hela systemet.

1 · FeatureSkapa, lista, visa, redigera, status, anteckning …
2 · KravObserverbart beteende med stabilt krav-ID.
3 · TestAPI-, UI- eller båda där kravet behöver det.
4 · KodFrontend, API och lokal lagring.
5 · KontrollGranska utfallet och kör relevanta tester.

Varför vertikalt?

Varje delsteg går att läsa, testa och följa från användarbeteende till lagring.

04 · Från krav till test

Ett konkret spår: CASE-EDIT-005

Ett krav ska gå att hitta i både specifikation och automatiserat test.

Krav i specen

CASE-EDIT-005

Om obligatoriska fält saknas ska uppdateringen stoppas och användaren få ett specifikt fel för varje fält.

Vad testet kontrollerar

  • Felmeddelande visas för tom rubrik.
  • Fältet markeras som ogiltigt.
  • Uppdateringsanrop skickas inte.
Krav-ID:t gör kopplingen sökbar. Själva testets innehåll måste ändå granskas.

1:25. Följ pekaren från kravtabell till testtitel och sedan till assertionerna: feltexten visas, fältet får aria-invalid och API-anropet görs inte. Testet täcker också CASE-EDIT-002; det är tillåtet att ett test täcker flera krav. Det här är konkret evidens, inte ett påstående att en titel ensam bevisar kvalitet.

05 · CI och kritisk granskning

CI gör kravtestningen synlig i varje pull request

Pull request-kontrollen

  • Krav-ID:n jämförs med kravmärkta testtitlar.
  • Nya krav ska ha nya tester i samma PR.
  • CI kör checker, API-/webbtester och build.

Vad kontrollen säkerställer

Varje krav-ID i kravtabellerna ska finnas i minst en automatiserad testtitel. Nya krav ska få nya tester i samma PR.

Projektresultat: 84 krav-ID:n hade matchande testtitlar.

106API-tester · godkänt
95webbtester · godkänt
6checker-tester · godkänt

Automatiserade resultat dokumenterade för projektet.

Begränsning: checker hittar ID:n i titlar, men vet inte om testet faktiskt bevisar kravet.

1:25. Förklara att CI körs vid pull request och kontrollerar krav-ID:n i testtitlar samt kräver nya tester för nya krav. Presentera testantal och 84 krav som dokumenterade projektresultat. Var tydliga med begränsningen: om en testtitel nämner ett ID utan att testa rätt sak, eller listar flera ID:n som testet inte täcker, räcker inte checker. Därför behövs gruppens granskning av testinnehållet också.

07 · Vad vi tar med oss

AI ökar farten — men ansvaret ligger kvar hos oss

Det som hjälpte

Små features, tydliga krav-ID:n och återkommande tester gav spårbarhet genom arbetet.

Det som krävde granskning

AI-förslag kunde missa relaterade ytor, felvägar eller ge tester med begränsat bevisvärde.

Vår lärdom

Vi granskade de första features mer noggrant än senare delar. En jämnare, återkommande kodgranskning hade stärkt processen.

Framåt: mindre ändringssteg och återkommande granskning — även om det tar längre tid — samt mer genomarbetad state- och routehantering.

0:55. Lyft den gemensamma lärdomen från underlaget: vi granskade de två första features mer noggrant och fortsatte senare med lättare kodgranskning och mer manuell testning. Det gav fart, men sänkte insynen. Berätta att mindre commits och jämnare code review vore ett bättre nästa arbetssätt. Avgränsningen är en lokal MVP, inte en produktionssatt tjänst.
